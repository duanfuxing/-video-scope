# 视频拆解—开发计划

日期：2026-11-10。状态：已实现并开始工程验证离线媒体准备基础；整片/开场语义拆解及正式结果包尚未实现，未做真实模型验收。功能说明、进度与计划入口统一见[VideoScope README](../../../README.md)。本计划及两份拆解格式在 VideoScope 仓库维护，消费方仅引用，不维护独立副本。

## 1. 决策与边界

- 独立仓库、Python 环境、配置、运行目录和任务记录；不导入 AgentCanvas 内部代码，不使用其 JOB、MySQL、Redis、模型配置或凭据。
- 独立工具负责读取视频、拆解、留存证据与导出结果包。AgentCanvas 后续负责导入、媒体归档、MySQL 权威存储、检索摘要编码与向量索引；工具不生成检索向量。
- 首版为单机命令行批处理工具，用固定程序编排，不依赖 Claude Code、Codex 或其他 Agent 运行时，不搭 Web 后台、HTTP 服务或分布式队列。
- 主分析模型确定为 Google Gemini 4 Argon，模型 ID 为 `gemini-4-argon`，通过 Google 官方 Python SDK `google-genai` 接入。首版不自动切换其他模型。
- 两种输出内容以[优质视频拆解 JSON](优质视频拆解JSON.md)与[黄金开场拆解 JSON](黄金开场拆解JSON.md)为基线，先保留中文业务键名。它们仍是待样本验证的内容讨论稿，不因模型选型完成就成为正式契约。
- 工具在独立机器运行，代码与运行数据分离；GitHub 仅保存代码和文档，不提交视频、抽帧、任务数据库、日志、模型权重或凭据。首次真实调用前落实样本、供应商上传许可和付费预算，不复用消费方密钥。AgentCanvas 导入器及流程 3 启用不属于本项目范围。

## 2. 首版操作与输入输出

调用方为操作人员或本机批处理脚本。首版只接受已合法取得的本地视频文件，不开发平台抓取、登录下载或签名链接刷新。

建议命令面如下，均为待实现接口，不是当前可执行命令：

```text
video-scope analyze <视频文件> --mode full|opening|both --output <输出目录>
video-scope batch <任务清单.jsonl> --output <输出目录>
video-scope status <任务标识>
video-scope resume <任务标识>
video-scope validate <结果包目录>
```

- 单条输入：本地媒体路径、模式、可选来源元数据；来源包括平台标识、链接、标题、类目、原文件是否完整及已知素材权限。未知信息不推断补齐。
- 批次输入：一行一个单条输入，保存独立任务状态；一个视频失败不阻断其他视频。平台长整数标识始终作为字符串处理。
- `full` 生成整片结果；`opening` 可独立生成开场结果；`both` 共用媒体处理与可复用证据，分别生成两份结果。
- 不以投放记录行作为视频唯一身份。同一文件按内容哈希复用基础处理，不把不同版本或不同剪辑凭相同标题合并；跨文件平台身份只是来源线索。
- 没有完整原片时，只记录实际观察范围，不将截取片段的结尾当作完整开场结束，也不补造后文承接。
- 结构检查通过仅代表结果可解析；拆解完成不自动认定为优质案例，不自动授予使用权限或开放检索。

## 4. 主模型与调用策略

### 4.1 主模型决定

选用 `gemini-4-argon`，因为本任务需要原始视频与音频联合分析，不能仅凭截图、ASR 文本推断动作音效和同步关系。2026-11-10 核对的官方目录明确列出其视频、音频、图片及文本输入能力，并将其定位为旗舰推理模型。

这是一项工程选型，不是样本质量胜出的实测结论；不从名称推断稳定版或生命周期承诺。开始实现时核对账号/地区可用性、SDK 支持和模型限制。不可用时明确报告阻塞，不静默换模型或中转服务。

使用供应商支持的结构化输出子集分模块请求。模型侧 Schema 保证不了内容真实，程序仍校验完整业务结果；复杂大 Schema 不一次塞入所有镜头与轨道。

首版不接备用分析模型，不增加另一个大模型专门把报告转 JSON。Gemini 3.8 Flash 仅列为后续降本候选，必须使用同一批视频和验收口径比较后才能替换，不能默认认定其达到本任务质量。

### 4.2 请求组织

- 整片先做一次上下文分析，确定内容阶段、实体候选和关键表现，再按镜头组完成全部基础镜头记录；单条长输入按供应商限制分段，不能静默截断。
- 相邻镜头成组分析以保留语境，不规定每个镜头一次调用；关键动作、开场或冲突区域再做局部补看。
- 开场模式先看片头与必要上下文，确认实际前三秒和完整开场边界；后文按承接需要查看，不默认先完成整片深拆。
- 同视频 `both` 共用基础证据，整片已覆盖的内容不完整重跑；开场边界、吸引机制与承接仍单独核对。
- 模型接收原始视听输入和带时间的基础证据，不把 ASR/OCR 候选当成不可质疑的事实。声音分析必须有音频输入，不能从静态帧猜音效。
- 抽帧、裁剪与模型返回时间统一映射到原视频起点；裁剪起点偏移由程序处理，不交给模型自行换算。
- 供应商默认低采样不能满足黄金开场精拆。全片上下文默认 static 1 FPS 有文档依据；开场/快速动作片段 8 FPS 仍只是待验证目标，当前官方文档未明确其允许范围，不能承诺支持。当前视频理解文档使用 Interactions API 的 `processing.type/fps/start_offset/end_offset`，不能混用其他 API 的字段名。切点和文字变化附近按原始帧时间戳局部核对，不把 8 FPS 当成精度保证，不上采样冒充新增证据。
- 小字或布局细节使用原画幅高分辨率关键帧补充；主体运动和相机运动分别描述，静态关键帧不代替动态证据。

## 5. 固定处理流程

1. **输入与媒体探测**：检查可读取性、音视频轨、时长、旋转、分辨率和帧时间戳；记录来源、完整性与内容哈希。可变帧率按实际 PTS 定位，不按帧号除以名义帧率计算。
2. **基础证据提取**：建立完整基础切镜候选；按分析范围运行 ASR、OCR、抽帧与片段准备。检测到闪光或包装变化不直接当作真实切镜，保留必要核对。
3. **范围与全局理解**：主模型识别内容阶段、实体及开场范围。只看过的维度与区间计入观察范围，不能因为上传了全片就标为逐帧核实。
4. **镜头与视听结构化**：按模式和镜头组输出动作、空间状态、运镜、声音、台词和文字包装。程序给记录分配唯一标识并维护映射，模型在限定标识范围内关联，所有引用都要可解析。
5. **参考与复刻分析**：从已有证据归纳创意、开场机制、迁移条件及素材依赖。观察与解释分开，不写新任务生成提示词、不证明原片功效、不推断素材授权。
6. **有限补看与校验**：只对具体遗漏、冲突、越界和关键定位补充证据。每个问题区域最多一次自动补看；仍不确定则明确记录，不无限循环，也不凭文本补齐没有看到的事实。
7. **结果包导出**：保存两种内容结果中实际请求的一种或两种，关联真实媒体文件，输出清单和质量状态。草稿/待复核可以导出，但不能冒充完整验收结果。

没有声音的原片可以正常处理并记录无音轨；音轨存在但转写失败不得伪装成无口播。OCR 无识别结果也不能直接证明无文字。缺少必需输入、模型请求失败、截断或格式无法解析时，任务标为失败/待处理而非成功空结果。

## 6. 任务、恢复与费用

- 单机单调度进程，任务之间允许有界并发；默认模型请求并发 1。媒体计算不持有 SQLite 写事务，不引入分布式锁、租约或服务集群。
- 缓存按视频内容、观察区间、处理参数、模型、提示词及契约版本区分；版本改变不能悄悄复用旧语义结果。
- 各阶段保存已完成产物。重启后显式 `resume`，只继续未完成阶段；导出失败只重做导出，不重跑已成功的分析。
- 明确未接受的限流等可恢复错误有限重试，最多两次，遵循供应商退避要求；关闭或协调 SDK 内建重试，避免两层重试相乘。已发送但结果未知的请求保留未知状态和请求线索，不盲目重复付费。
- 每次请求记录模型、阶段、输入区间、采样参数、提示词版本、请求标识（若返回）、耗时、usage、错误与重试次数；不记录密钥或私有签名 URL。
- 费用按主分析、局部补看、重试分别汇总，区分返回的 usage、估算费用与供应商最终账单；音视频输入和思考输出纳入统计，失败请求费用不默认算零。
- 真实调用前需要明确授权视频范围、允许的调用类别与总预算。批次和单视频设调用次数/费用停止条件；单次最大输出和在途请求成本需预留，不能把本地估算预算声称为供应商硬限额。
- 向 Google 上传媒体属于外部数据传输，使用前确认素材可交由该供应商处理，核对地区和数据保留政策。工具只清理自己创建的供应商上传对象，不清理共享资源。

## 7. 结果包与契约归属

建议目录（交付形状，尚不是正式 manifest Schema）：

```text
<视频结果包>/
├── manifest.json
├── full-video.json        # 按模式存在
├── opening.json           # 按模式存在
└── media/
    ├── source.mp4         # 实际保留原扩展名，不为此强制转码
    ├── frames/
    └── clips/             # 仅存实际需要的派生片段
```

- 首版采用自包含目录包：携带获得授权可交付的原视频及实际引用关键帧；动态证据优先引用原视频时间范围，不重复裁出每个片段。无交付原视频权限时不自动生成可供下游使用的媒体包。
- manifest 保存包格式版本、来源身份、媒体哈希和相对路径、分析修订、输出文件清单、实际模型与配置版本、观察完整性及待复核状态；不含本机绝对路径、密钥或供应商临时文件 ID。
- 媒体引用由程序生成并检查文件存在；禁止模型编造 URL。结果内容引用的是包内来源标识，不是 AgentCanvas 数据库 ID；导入方负责身份映射。
- 导入方按来源与分析修订处理重复包，校验版本、引用、哈希及路径；未支持版本、越界路径、缺失媒体不得静默当成功导入。具体导入实现不属于独立工具首版。
- 正式导出 Schema 在 VideoScope 的 `contracts/` 中作为唯一上游契约维护并版本化；消费方按已发布版本消费，不独立修改副本。AgentCanvas 自己的导入接口及内部运行契约仍归 AgentCanvas 仓库的 `contracts/`，两者不是同一个契约。
- 现有两份 Markdown 只作内容基线。正式 Schema 需把未知值、空列表、未观察范围、引用类型和包内路径落实为可验证规则，不把示例的 0/空串当成默认事实。

## 8. 实现顺序与验收

### 阶段一：单视频整片闭环

在独立项目实现最小 CLI、媒体处理、主模型接入、整片结构校验和导出。直接用一条已授权真实视频验证，不先建设通用 Agent 框架、模型路由平台或大规模基准系统。

### 阶段二：开场与共用证据

实现 `opening` / `both`，重点验证跨三秒台词、镜头内部的开场边界、快速动作和后文承接，确认不会重复跑完整基础处理。

### 阶段三：批处理与恢复

增加任务清单、SQLite 状态、断点续跑、缓存和费用统计；验证一条失败不影响其他条目、已成功阶段不会因导出失败重复收费。

### 真实验收集合与完成标准

初始使用 12 条实际来源视频，不合成假视频作为业务通过证据。样本覆盖口播、产品操作、快切、人物对话、录屏、复杂文字、强背景音乐等，包含至少一条不足三秒的视频；至少 4 条执行 `both`。对照原片人工标注关键镜头、开场边界、关键词和同步事件。该规模仅用于首版验收，不推断全量案例准确率。

- **结构与文件**：所有成功包均可解析，引用唯一且可解析，时间不越界、媒体路径可解析；缺失与未知明确记录，不得静默丢字段或截断。
- **整片覆盖**：完整基础镜头表覆盖全片，无无说明的漏镜、空洞或重复区间；过渡单列，不与镜头重复累加时长。
- **硬切定位**：针对可明确判定的硬切，与人工逐帧核对值误差不超过 2 个原片帧；叠化等模糊边界单独记录区间，不伪装成精确硬切。
- **开场与同步**：对人工可明确定位的关键台词、动作与声音事件，时间误差目标不超过 0.2 秒；完整开场的语义边界由人工核对依据，不机械按 3 秒裁断。无法达到的记录标为不确定，不计为精确定位通过。
- **内容正确性**：逐条核对核心买点原文、主体操作、动作方向、文字类别与后文承接，不能出现改变理解的错误；原片主张、观察事实与迁移建议明确分开。发现错误当轮修复并重跑受影响场景。
- **可用性**：所有 12 条都要有明确处理结论；至少 10 条达到目标模式的参考可用标准，其余说明原始资料限制或真实失败。不能靠把所有内容写成不确定项来通过；复刻所需关键证据缺失的结果单独标为待补，不声称可高还原复刻。
- **恢复与成本**：真实验证本地中断、导出失败后的恢复及重复输入复用；保留每条耗时、调用次数、usage 和预算记录。不制造昂贵重复调用来测试，不以离线替身证明供应商链路通过。
- **检查**：Ruff、mypy，以及真实 CLI、媒体和供应商结果核对。没有 Web、MySQL/Redis 的独立工具不为验收接入这些设施；未来 AgentCanvas 导入与检索另行按其真实环境验收。

上述为待达成标准，不是已经通过的证据。付费预算和真实样本未获授权前，只能完成非付费部分，不能宣称主模型适用性已验证。
